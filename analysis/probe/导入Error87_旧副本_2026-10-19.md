# 仙女棒手机包导入 Error 87：12:06 的修复没生效到文件入口（导出（23），2026-10-19）

用户 10-19 19:45：「gpt一直修不好……手游的导入失败，PC的可以，而且Gpt好像修错地方了」。截图：19:39:27 SkyRocketSparkler_01「导入完成（97.3s）：已保存 5 项…」→「导入中止：UE Python 出错 … subprocess.py _execute_child … WindowsError: [Error 87]」。

## 结论（已核实：导入器（5）20:23 读 UE 日志，`analysis/probe/导入文件入口复核_20261019.md`）

GPT（导入器（5））对 Error 87 的判断（累计证明塞进启动命令超过 Windows 32,767 字符）和修法（2.29：证明走 stdin）是对的，但只部署到私有源文件 `D:/FXTools/DFWorkbench/df-fireworks-delivery_locmai.html`，验证也只做了 8034 HTTP 入口。

用文件方式打开烘焙器（`file:///…/tool/FireworkBaker.html`）时，交付页加载的是本机副本 `tool/local_delivery/runtime/importer.html`（gitignore）。副本只在 `启动烘焙器.cmd` / `tool/build.py` 运行时由 `prepare_local.py` 生成；`启动全部工具.cmd`（`tool/local_http/launcher.py`）注释写明「不调用prepare或重新生成私有文件页面」。12:06 以后没人重新生成 → 文件入口还是 2.28。

依据：
- **UE 日志（导入器（5）读的）**：19:39 实际启动命令 36,605 字符，用的是旧 `--register --proofs`、没有 `--proofs-stdin`，目录是 PC 包——PC 资产保存后登记中止，手机包还没开始。F 盘副本 20:10 已换成 2.29。
- 19:39 的日志措辞是 2.28 的「导入完成 → 导入中止」；2.29 把它改成「资产写入完成，待交付登记」（`analysis/probe/导入收尾修复_2.29.md`、计划 Task 2）。
- 代码：`67_delivery.js` 文件入口 iframe 指向 `local_delivery/runtime/importer.html`，HTTP 入口指向 8034 `/delivery-host`（服务每次现读源文件）。
- 「PC 可以、手机失败」：旧版先导完 PC 资产（UE 里已保存 5 项）才在登记那步报错中止，手机包还没开始；证明随每次登记变长，后一包更容易超长。

## 修法（烘焙器 4.9.119）

副本带来源戳；8034 服务发现副本旧了自动重新生成；烘焙器文件入口比对「交付页实际加载的戳」和「源文件戳」，不一致重载一次，还不一致（或副本没戳、服务又是旧进程）就拦下导入并写清修法；两个启动入口都重新生成副本；服务代码更新后旧进程还在跑会提示。详见 `tool/CHANGELOG.md` 4.9.119、`tool/local_delivery/README.md`。
