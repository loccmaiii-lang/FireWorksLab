# 导入登记 Error 87 走查与修复

日期：2026-10-19；对象：烘焙器的独立资源交付入口，私有构建 v2.29。

## 已确认原因

用户截图中的 Sparkler_Graph 在 11:31:22 先有贴图、材质、粒子保存/添加成功回执，随后交付登记失败。真实 UE 日志对应启动命令为 **36,000 字符**，超过 Windows CreateProcess 的 **32,767 字符**上限。私有 `delivery-contract.js` 把累计核验记录全塞入 `--proofs` 参数；共享记录已121条，浏览器还持有本次新增记录。不是该效果的命名、像素或粒子模块配置错误；随着导入数量增长会重复触发。

此前测试只用少量记录、模拟子进程成功，没有覆盖累计数据和真实 Windows 启动限制。原生导入已经打印“完成”，外层登记异常又统一标成“导入中止”；失败后仍查看未开始的手机包，进一步掩盖实际阶段。

## 修复与恢复

- `delivery-contract.js` / `delivery-preflight.py`：固定长度的启动命令，证明通过 UTF8 stdin 传输；Python2.7 的 communicate 同时收发，base64仅用于安全生成内嵌字节。不删除历史证明，旧小规模参数入口兼容。无效JSON/UTF8/非对象在登记前拒绝。
- `build-delivery.py`：原生日志只报告资产写入完成；登记成功后才报告交付完成。登记错误携带真实保存/版本管理计数与正确阶段，定位失败包，显示“已保存 · 登记待补齐”。
- 只有全部所选目标都有保存回执、且确为登记阶段失败（包括旧Error87）时，才提供 **补写交付登记（不重导资产）**。用户点击后重读来源及目标映射，检查资产类型、来源标识、未保存改动、文件存在与贴图保存哈希；通过后只补登记。缺失证明、变更或错误不会触发重新导入。
- 本轮未触碰真实 UE、P4、用户浏览器数据或真实资源登记；没有自动恢复这次任务。原工作台和原始工具保持改前原字节；效果/渲染/命名/素材与NoMip等既有规则保持。
