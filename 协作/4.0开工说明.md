## 0. 一段话讲清楚

**项目**：网页烘焙器 `tool/FireworkBaker.html` 负责模拟写实日式烟花，把它烘成序列贴图和 `cascade.json`，给 UE 4.24 Cascade 用（MMO 项目）。

**现状**：烘焙器停在 3.7，几十个效果都是在旧底层上一层层打补丁做出来的。

**问题**：底层有系统性问题，都写在 `协作/渲染基础问题清单.md`，下面是最主要的几条：

- **看到的不是导出的**：实时模拟、导出效果、对照图三处用的分辨率、运动模糊、曝光各算各的。
- **滑杆失效**：尺寸滑杆在导出分辨率下大多没用；把光点放大只会让它变糊。
- **帧预算不按引擎来**：开花段塞进大量引擎显示不到的帧，后段又卡顿。
- **格子太小**：贴图格子 256 px，用户要求 PC 至少 512 px（这是下限；要更清楚的效果用 1024 或 2048 的格子）。
- **导出有缺**：多层效果不是一个素材包；手机版和 PC 版完全相同。
- **体验不统一**：有的条目有「游戏内大小」「流转动画」，有的没有。
- **没有及格线**：自检不判定通过与否，这些问题一直漏过去。

**你的任务**：把烘焙器做成 **4.0**，分三件事：

1. 按 `协作/标准.md` 把底层整理干净：一个渲染核、按引擎帧率分配帧、一个条目查看器、自动的标准检查。
2. 花型库按新标准重调，做出「第一眼就惊艳」的效果。
3. 再把正在做的效果迁过来。

**用户的期望**：「1.0 的版本给我感觉很惊艳，我希望 4.0 也可以同样做到类似的效果。」1.0 是这个烘焙器的第一个可视化版本（当时没有这么多补丁，画面干净、统一）。所以 4.0 **最先能被用户看到的成果**，要让花型库打开就好看：

- 星头亮核清晰，不是一团糊；
- 火花细节丰富；
- 运动稳定，不闪、不抖；
- 在游戏内大小下依然清楚。

### 阶段 4.0-a · 一个渲染核（最重要，用户最先能看到的变化）

目标：光点尺寸在任何分辨率下都有效；放大 = 更大的亮核，不是更糊；三个画面同一套快门、曝光、光点。只对 `renderVer >= 40` 生效。

1. **光点模型**（`40_gl.js` 的 `VS_PTS` / `FS_PTS` / `emitPt`，GPU 火花路径同样处理）：
   - **去掉 0.55 px 的 σ 下限**，改用像素覆盖积分（`05_quality.js` 精细档里已有的 `coverage()`）处理亚像素。
   - **尺寸的含义**：size = 亮核直径（米）。
     - 亮核：边缘有 1 px 过渡的实心圆盘，**面亮度恒定**（亮核越大，亮的面积越大，不是越暗）。
     - 光晕：另加一个高斯，参数 `haloFrac`（光晕能量占比）、`haloR`（光晕半径 / 亮核半径）。
   - **亮核小于 1 个渲染像素时**：总亮度 ∝ 面积，所以滑杆仍然有反应——画面变亮，而不是没反应。
   - **6σ 方框**：改成径向窗口（问题清单 B8）；点尺寸超过 `PT_MAX` 时，改画一个四边形。
   - **验证**：
     - 写一个尺寸扫描检查：同一配方，headSize = 0.3 / 0.6 / 1.2 / 2.4 m，按导出的单格分辨率（先试 512，再试 1024）`renderStills`。量「亮度 > 半峰的像素数」，必须随尺寸单调增加；量峰值亮度，不能随尺寸下降超过 10%。
     - 探针的「尺寸参数有效」要变成 ✅。
2. **快门统一**：
   - 写一个函数 `shutterWindow(P, plan, t)`，返回 `[t − W/2, t + W/2]`，其中 W = `P.shutter` × max(该帧显示时长, 1/30 s)。
   - `renderLive`、`bakeFrames`、`renderStills` 都调用它。实时页按「当前时刻对应的导出帧」取 W。
   - 滑杆标签改成「运动模糊（占每帧显示时间的比例）」。
   - 验证：同一时刻三处出图，拖尾长度差 < 10%。
3. **曝光**：
   - 新行为默认用**固定曝光**：配方里加 `exposure`，旁边一个「按当前画面建议」按钮，按下时用自动曝光算一个值填进去。这样亮度滑杆才真的有用。
   - 自动曝光统计时排除开花闪光（问题清单 C1）。
   - 加「锁定曝光」开关（问题清单 C2）。
   - 验证：headBright × 2 → 导出贴图里星头的平均值 × 2（±10%，没过曝时）。
4. **引擎回放画面**（把现在的「导出效果」页升级）：
   - 按 30 fps 的 tick 取帧：帧号 = floor(曲线(t_tick))，和材质一样。
   - 默认用「游戏内大小」。观察距离滑杆 800–1200 m，默认 1000 m。换算用用户实测：四尺玉在这个距离约占屏高 1/3，按花径换算屏幕像素；条目可以写 `screenFrac` 覆盖。
   - PC / 手机可以切换，按各自实际导出的格子显示。
   - 预览光晕（`FS_POST` 的 mip 光晕）默认关，UE 的 Bloom 另算。
   - **所有产物都要有**：大面片、分段、尾缀、单元、组合（用户明确要求写进标准）。
5. **实时模拟**加一个开关「按导出分辨率预览」：先按导出的单格分辨率渲染，再放大显示。调参时看到的就是导出会得到的。
6. **给用户的第一个成果——「橱窗」**：

   - 可以是烘焙器左栏的一个入口，也可以是 `analysis/probe/橱窗/` 里的对照图 + 更新记录一条。
   - **在这一步请用户看**：光点质感、清晰度、亮度，是不是「1.0 那种惊艳」。按他的意见调光点和曝光的默认值，再往下做。

### 阶段 4.0-b · 帧预算和格子（按引擎来）

用户定的规格：引擎 30 fps；PC 单格**最小** 512 px，手机**最小** 256 px。这些是下限，不是固定值：有的效果需要更清楚，就用 2×2（单格 1024）或 1×1（2048）。帧不够就加贴图张数，不能缩小格子。**不要把规则定死**：用户明确说过，死板的规则会造成误解。

1. **帧号曲线**（`30_plan.js` 的 `plan()`）：
   - 帧密度上限 = 30 帧 / 秒，下限按标准（燃烧段 12、淡出段 8，AI 提议值）。
   - 先算「理想密度」（现在按速度），夹在 [下限, 30] 之间，再归一化到总帧数。
   - 总帧数不够下限时：算出需要几张贴图。
2. **格子**：
   - **格子每个效果自己选**：PC 在 4×4（单格 512）、2×2（1024）、1×1（2048）之间选，都乘 RGBA 四个通道。
     - 默认按「屏幕放大 ≤ 1」和清晰度需要，选能满足的最小格子数；用户或条目可以指定更大的格子（条目参数 `cellPx` 或 列 × 行）。
     - 烘焙器给出建议（「这个效果在游戏内大小下 512 格放大 1.3 倍，建议 1024」），但不自动锁死。
   - 长效果自动分成 N 段（`50_bake.js` 现在只支持 A / B 两段，要改成 N 段，`cascade.json` 也要写 N 个发射器或分段）。
   - 手机单独烘：单格至少 256（例如 1024 贴图 4×4×4，或 2048 贴图 8×8×4）；细节多的效果可以更大；帧数和 PC 对齐。
3. **首尾裁帧**：
   - `trimLead` 已经裁开头；再加 `trimTail`，裁掉末尾全暗的帧，缩短寿命。
   - 延时出现的层（千轮子花等），开头空白用发射器延迟补（问题清单 B3，片贝第 2 层有 109 个空帧）。
4. **防混叠**：
   - 点灭频率超过「0.4 × 该段帧率」时报警，建议改成粒子。
   - 火花闪烁按物理时间取随机数（`hsh(uid, floor(t × 闪烁频率))`），不要每个子样本都重新取（问题清单 E5、E6）。
5. **验证**：
   - 探针在全部基准上：30 fps 下显示帧 ≥ 90%、燃烧段有效帧率 ≥ 12、单格不小于下限（PC 512）、屏幕放大 ≤ 1；
   - `--bake` 核对实际格子；
   - 回放检查：中心跳变 ≤ 3 px。
6. **出一个样片请用户进引擎看**：12 fps 这条下限是 AI 提的，用户在引擎里看过才算数。建议用四尺玉（鸿巢主层）PC 版，分 2–3 张贴图。

## 6. 容易踩的坑

- **不要把用户给的数值当成固定值**：用户说的「最小 512」「手机 256」「30 fps」「800–1200 m」都是条件或下限。每个效果按自己的内容选格子、张数、帧数，并说明理由；拿不准就问。这份交接里的及格线（12 / 8 fps、放大 ≤ 1、显示帧 ≥ 90%）是用来拦住明显问题的，不是每个效果都必须做成一个样。

- **已通过的东西不能悄悄变**：每次改渲染都跑 `烘焙器回归.py --legacy`，必须 0 差。
- **生成文件**：`tool/FireworkBaker.html`、`tool/data/*.js`、`协作/状态清单.md` 不手改。rebase 冲突时拿对方的版本，再重新跑 `review_to_baker.py` 和 `build.py`。
- **`tool/data/review.js` 约 3 MB**：生成比较慢（要算视频取景），耐心等。
- **颜色段最多 5 段**。
- **一个发射器只有一条颜色曲线**：星头和尾巴颜色不同时，拆成同一模拟的两层（同种子、同初速、同星数）。
- **大面片只用固定 / Zoom 取景**：紧凑取景在引擎里会抖，已经禁用。
- **引擎硬约束**（`CLAUDE.md` 第 2 节）：不新增材质、引擎里不写代码、帧号走 Dynamic Parameter 第 3 通道、不做帧间混合、Ramp + Color Over Life。烘焙器和脚本的代码随便改。
- **Codex 也可能在用户电脑上推 main**：4.0 期间它不改 `tool/src/`。看到它的提交先读，冲突保留双方。
- **软件渲染**：Linux 下的截图和性能不代表真显卡。例如 `PT_MAX`（点精灵尺寸上限）各平台不同，要在用户电脑上核对。
- **不要用拟合分数判断好坏**：4.0 是工程工作。判断看探针、回归、标准检查的数字，以及游戏内大小的画面。
