# FireWorksLab：给 AI 的项目说明（v2 草案 2026-09-30）

> 适用于所有 AI 执行方：云端 Claude、Codex（同内容放在 `AGENTS.md`）、定时接续会话。
> 判断「做完没做完」只看 `协作/标准.md`。本文件讲做事的方法和协作规则。

## 0. 开工三件事

1. `git fetch` → `git log HEAD..origin/main`：先读别人新推的提交。
2. 读 `协作/状态清单.json`，跑 `python3 analysis/scripts/待处理.py`，再读自己对话的 `对话记录/对话框<N>.md` 最后一条。
3. 要动的效果或底层，先在状态清单里认领（写上「负责」）、推送，再动手。

## 1. 目标

UE 4.24 MMO 用的写实日式烟花素材。在 `tool/` 的网页烘焙器里模拟、烘焙成序列贴图，导出素材包，在 Cascade 里搭建。

- **好不好只看引擎里的样子**：以烘焙器的「引擎回放」（导出贴图按 `cascade.json` 播放）为准。实时模拟只用来调参；对照图、拟合分数只是测量工具。
- **参考视频**：只用来定原理、颜色、时间、比例。输出形式按花型库 / 正式库：大面片用固定或 Zoom 取景，尾缀用 V5 形式。不照搬实拍的机位和构图。
- **「通过」只由用户决定**：AI 自检通过、拟合分数低，都不等于通过。

## 2. 引擎硬约束（不能违反）

- 只用 Cascade 和项目里已有的发射器、材质、贴图：**不新增材质，引擎里不写代码**。烘焙器和脚本的代码可以改。
- 帧号走 Dynamic Parameter 第 3 通道，材质里取整，不做帧间混合。
- 序列贴图：灰度、RGBA 接力（R 填满再 G、B、A）、BC7、2048。用户要求时才另出 4K 母版。
- 颜色来自 Ramp 贴图 + Color Over Life。一个发射器只有一条颜色曲线：星头和尾巴颜色不同时，拆成同一模拟的两层。
- 大面片只用「固定」或「Zoom」取景（紧凑取景在引擎里会抖，已禁用）。
- 素材包按 `spec/`：一个效果一个目录，`T_<效果名>.png`、`_Ramp`、`_Cutout`、`cascade.json`（PC）+ `cascade_mobile.json`（手机）。正式名字由用户本机的导入工具决定。
- PC、手机两套都要。尽量降低 overdraw。
- 细节不能超过来源：要 2K / 4K 的细节就用程序渲染，实拍只作对照。

## 3. 做一个效果

1. **原理**：对照花型库模板，写清楚——
   - 分几层，每层的轨迹关系（同一批星的不同阶段必须是同一个模拟）；
   - 颜色时间线、有尾无尾、熄灭方式；
   - 烘焙器还缺什么能力。

   写进 `analysis/原理/<效果>.md`。不等用户逐项核对；只有参考确实判断不了、而且不同选择会明显改变目标时，才集中问，并附上推荐。
2. **结构先对**：模板表达不了，就先补通用能力（按 `标准.md` 第 3 节），不指望拟合去补结构。
3. **调**：
   - 按「开花后同一秒」和实拍对照，用 `时刻对照.py` 在云端快速看、快速改。
   - 拟合只调少数连续量（亮度、大小、星数、时间），并且只在参数有效的范围里调。
   - 相机模糊 / 曝光只用来测量对照，不进素材，也不能靠它「调得像」。
4. **不许走捷径**：调暗某层、隐藏关键特征、模糊画面、改取景来降低误差，都不行。连续两轮没改善，就重新诊断模型或目标，不加算力硬跑。
5. **交付**：导出 → `标准检查.py` 全部 ✅ → 在引擎回放里亲眼看关键时刻、连续播放、整体、局部 → 每个效果只交**一个**推荐候选，进「待我验收」。
   - 附一段简短说明：解决了什么、还有哪些不影响主要目标的差异、哪些没经过 UE 验证。
   - 做不到时，集中报告卡在哪、试过什么，不交半成品。
6. **用户通过后**：搬进正式库，锁住当时的烘焙器版本。以后只改形式（取景、格子、命名），不改效果。

## 4. 改烘焙器 / 管线

- 发现系统性问题（渲染、帧预算、曝光、导出），**先停掉受影响效果的任务，修底层，再继续做效果**。当前待修清单见 `协作/渲染基础问题清单.md`。
- 按 `标准.md` 第 3 节做：分层、能力通用化、升版本号、`tool/CHANGELOG.md`、回归、先写检查再修。
- 改完源码必须跑 `python3 tool/build.py`，再提交。

## 5. 分工与协作

- **用户**：给参考、说审美方向、做最终验收、决定标准。不替 AI 找实现错误，不做中间检查。
- **负责该效果的 AI**：
  - 从原理一直做到交付；结果回来自己看、自己迭代，不默认转交用户；
  - 烘焙器底层同一时间只由一方改（在状态清单的「共享文件」里认领）。
- **本机显卡**：后台脚本每 30 分钟取任务、计算、导出、上传。它没有视觉判断，结果要由 AI 看。重的计算和导出交给它；云端没有显卡，只做抽查。
- **定时接续会话**：遵守同一套规则；底层在修的时候暂停。
- **多方同推 main**：
  - 小步提交，推之前 `git fetch`；
  - 有新提交就 `git rebase origin/main`，冲突时保留对方内容再加自己的，**绝不 force push**；
  - 生成文件（`tool/FireworkBaker.html`、`tool/data/*.js`）冲突时拿对方版本，重新生成；
  - 用户认可的东西（正式库、默认值）只在用户明确要求时改。

## 6. 记录：每样东西只记在一个地方

| 记什么 | 记在哪 | 什么时候写 |
| --- | --- | --- |
| 用户原话 + 拆好的步骤（勾选框 + 提交号） | `对话记录/对话框<N>.md`（每个对话一份） | 收到消息先写，每做完一步打勾，推送 |
| 每个效果的状态、负责人、版本、下一步 | `协作/状态清单.json`（唯一） | 状态变了就改 |
| 做了什么的日志（给接手的 AI） | `交接.md` 第 5 节，一段一条 | 每完成一个工作段落，推送 |
| 给用户看的更新 | `更新记录.md` 顶部 | 只写进了「待我验收」的，或需要用户做的事 |
| 某个结果的评审 | `analysis/results/<id>/看法.md` | 看完结果就写 |

- 会话随时可能断：没推上去的等于没做。推不上去时，先告诉用户，并把交接写进 claude.ai Project 的文档。
- 目录结构变了，同步改 `仓库梳理.md`。

## 7. 用户怎么看结果

- 用户只做一件事：`git pull`，刷新 `tool/FireworkBaker.html`，看左栏「待我验收」（另有：制作中 / 已通过 / 历史）。
- 条目数据由 `python3 analysis/scripts/review_to_baker.py` 生成。被取代的版本进「历史」，不删。
- 审阅标记按「条目 + 版本指纹」存在用户浏览器里；「复制我的意见」贴给 AI。
- 视频不是交付物，默认不录（任务里不开 `video`）。

## 8. 在聊天里给粒子参数

- 按 Cascade 里实际的发射器、模块、字段顺序逐项列，给可以直接复制的数值。
- 曲线给完整关键帧。颜色（0–1）和亮度倍数分开写。
- 单位用 Cascade 原生单位（cm、cm/s、秒、圈），和 `spec/cascade_params_v1.md` 一致。

## 9. 目录

| 目录 | 放什么 |
| --- | --- |
| `tool/src/` | 烘焙器源码，`build.py` 合成 `tool/FireworkBaker.html` |
| `tool/data/` | 生成的数据 |
| `analysis/scripts/` | 测量、对照、拟合、导出检查、标准检查 |
| `analysis/jobs/` | 本机任务；起点放在 `analysis/jobs/起点/` |
| `analysis/results/` | 本机结果 |
| `analysis/local/` | 用户本机脚本 |
| `analysis/原理/` | 效果原理和条目 |
| `spec/` | 导入方案（`fwl.cascade/1`）、UE 实测记录 |
| `vidio/` | 参考视频 |
| `协作/` | 标准、状态清单、问题清单、接续 |
| `归档/` | 不再使用的历史资料 |

每个目录现在有没有用、有哪些冲突，看 `仓库梳理.md`。
