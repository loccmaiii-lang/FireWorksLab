# 给其他 AI 的执行说明（GPT / Codex / 新的 Claude 会话都适用）

> 用途（用户 2026-09-30 要求）：云端 Claude 额度不够时，用户可以把这里的任务交给别的 AI 做。
> 写给「没参与过前面对话」的执行者：照着做，不要自由发挥。拿不准的，停下来问用户，或者把问题写进 `交接.md` 第 3 节。
> 维护：云端 Claude 每次调整计划时更新第 4 节「任务清单」。

---

## 1. 开工前必读（按顺序，约 10 分钟）

1. `git pull`，`git log -10`，看有没有别人刚推的提交（多方会同时推 main）。
2. `交接.md` 第 0–3 节：当前状态、待办、在等用户什么。
3. `CLAUDE.md`：项目硬约束和协作规则（下面第 2、3 节是摘要，冲突时以 CLAUDE.md 为准）。
4. `对话记录/对话框<N>.md` 最后一条「进行中」：用户最新的原话和已拆好的步骤。
5. 要做的效果对应的原理文档：`analysis/原理/<效果>.md`（用户核对过的结论在文末「用户核对结果」）。
6. 最新审阅意见：`analysis/reviews/` 里时间最新的文件。

## 2. 硬约束（违反就返工）

**引擎侧**
- 目标是 UE 4.24 **Cascade**；只用项目已有的发射器、材质、贴图：**不新增材质，不写引擎代码**。
- 序列帧：帧号走 Dynamic Parameter 第 3 通道，**不做帧间混合**；灰度 **RGBA 接力**（R 填满再 G、B、A）；BC7；导出 2K（2048），格子贴合内容，四个通道用满。
- 颜色来自渐变贴图（Ramp）+ Color Over Life。一个图层只有一条颜色曲线 → 星头和尾巴不同色时要拆成两个图层（同一个模拟、同种子）。
- 大面片取景只用「固定」或「随开花放大（Zoom）」；**紧凑取景禁用**（引擎里抖）。
- 导出素材包：`T_<效果名>.png`、`_Ramp`、`_Cutout` + `cascade.json`（PC）+ `cascade_mobile.json`（手机），格式 `spec/cascade_params_v1.md`（`fwl.cascade/1`）。
- 在聊天里给粒子参数时：按 Cascade 实际模块、字段顺序逐项给可复制数值；曲线给完整关键帧；颜色和亮度分开写。

**做效果的方法**（用户多次纠正过，最重要）
1. **先原理，后参数**：新效果先逐帧看参考视频，写原理解析（对应花型库哪个模板、几层、每层颜色时间线、有无尾、熄灭方式、烘焙器缺什么），配关键帧截图，**给用户核对**。用户没核对前不下拟合任务。
2. **按花型库 / 正式库的形式迭代，不照搬参考镜头**：输出是游戏素材的镜头和形式（例：尾缀用 V5 的弹体坐标、16×1 循环 + 消散）。参考视频只用来定原理、颜色、时间、比例。
3. **拟合分数低 ≠ 通过**：只有用户在迭代区点「通过」才算。
4. **拟合不能把层调没**：拟合的打分不看颜色，会把芯、星头层调暗到看不见来换分数（QA5 / QC4 / QD4 就是这样）。多层效果拟合时**固定各层亮度**（不放进 `fit.params`，或用 `caps` 给下限），只放开大小、速度、星数、尾长。
5. 共用一个模拟的层（尾巴层 + 星头层）：初速、星数、种子、风、湍流**必须完全相同**，不能分层拟合。

**不要做的**
- 不要改用户已认可的东西（正式库条目、尾缀 V5 默认值），除非用户明确要求。
- 不要在金芒菊清晰度上花时间（用户：Zoom 能用就行，高清化以后用 Ultra）。
- 不要 `git push --force`；不要删别人的文件；不要手工合并生成文件（见 3.4）。

## 3. 协作规则

### 3.1 多方同推 main
- 开工前 `git fetch` + `git log HEAD..origin/main`，先读别人的新提交。
- 小步提交、做完一段就推；推前再 fetch，有新提交就 `git rebase origin/main`，冲突时保留对方内容再加自己的。
- 开始较大的改动前，在 `交接.md` 第 2 节对应待办标「进行中 · 你是谁」并先推一次，避免两方同时改一处。

### 3.2 记录（会话随时会断）
- `对话记录/对话框<N>.md`：用户每条消息先照抄原话，写「理解与编排」（勾选框步骤），推送；每做完一步打勾、写提交号，再推。
- `交接.md`：每完成一个工作段落更新第 1–3 节，第 5 节顶部加一条日志（做了什么、结果在哪、没做完什么）。
- `更新记录.md` 顶部加一条给用户看的说明（烘焙器顶栏「更新记录」显示它）。

### 3.3 用户怎么看结果
- 用户只做：`git pull` → 刷新 `tool/FireworkBaker.html` → 左栏「迭代区」。
- **迭代区一个效果一条**：多层效果是「组合条目」（点开进组合页，实时模拟整体 + 实拍并排），各层隐藏、在审阅卡里单独打开。
- 每条都要是正式库形式：右栏参数齐全、实时模拟 / 导出效果 / 贴图三页有内容、能导出。**不能只有视频对比**。
- 条目怎么加：
  - 原理样机 / 手配条目：`analysis/原理/条目*.json` 或 `analysis/迭代/条目.json`（`entries` 是层，`combos` 里带 `id` 的是组合条目）。
  - 拟合任务：`analysis/jobs/<id>.json` 带 `review`；多层用 `start` 里的 `layers`。跑完自动出组合条目。
- 生成：`python3 analysis/scripts/review_to_baker.py`，然后 `python3 tool/build.py`。

### 3.4 生成文件
- `tool/FireworkBaker.html`、`tool/data/review.js` 是生成的：rebase 冲突时拿对方版本，然后重新跑上面两条命令。

### 3.5 显卡任务
- 用户电脑有后台监控（每 30 分钟检查 main），新任务会自动跑并推结果；写好但先不跑的任务加 `"ready": false` + `"hold": "原因"`。
- 结果在 `analysis/results/<id>/`：`对照.jpg`（上实拍、下模拟）、`数值.json`、`best.json`。看完写 `看法.md`。
- 云端没有显卡：`analysis/scripts/compare.py` 在 Linux 上走软件渲染，只用来抽查起点（2K 精细采样会超过 10 分钟）。
