## 项目是什么

UE 4.24 MMO 的写实日式烟花特效素材。在 `tool/` 的网页烘焙器里模拟、烘焙成序列贴图，再按导出的参数表在 Cascade 里搭建。

硬性约束（不能违反）：
- 只能用 Cascade 和项目里已有的发射器、材质、贴图：**不新增材质，不写代码**。
- 帧号走 Dynamic Parameter 第 3 通道，不做帧间混合。
- RGBA 接力（R 填满再 G、B、A），灰度，BC7，只导出 2K。
- 颜色来自渐变贴图 + Color Over Life。
- 尽量降低 overdraw。

贴图分辨率规则（用户 2026-09-28 明确要求，必须遵守）：
- **分辨率最大化，以 2K 为准**：每张序列贴图都做满 2048（2048×2048，或至少 2048 宽），不为省显存降到 1024 或更小。需要时先出 4K 母版（4096），由用户自己压缩。
- **RGBA 四个通道都用满**：RGBA 接力就是用来换更大的格子或更多帧的，默认四个通道全部填满，不留空通道。
- **格子贴合内容**：按内容长宽比选列 × 行，让每帧内容尽量占满格子，细节清晰、丰富。
- **细节不能超过来源**：从视频直接截取的素材分辨率受视频限制，放大不会更清晰；要 2K / 4K 的真实细节，就用程序渲染，实拍只作对照标准。

## 进入「待我验收」的条件（AI 必须亲自检查，缺一条就留在「制作中」）

1. 完整效果的主要造型、层次、配色、节奏和参考一致（关键时刻 + 连续播放 + 整体 + 局部都看过）。
2. 已发现的明显问题已修复，不把「知道怎么修但还没修」交给用户。
3. 实时模拟和实际导出贴图的回放都检查过；组合层没有缺失、错位、裁切、异常曝光。
4. 按项目规范生成贴图、Ramp、Cutout、参数、`cascade.json`（PC + 手机）素材包，且和当前版本一致（导出清单里的版本指纹 = 条目的 `ver`）。
5. 烘焙器里能看完整效果预览、参考对照、参数、贴图、导出入口，不是只有一张对照图或视频。
- 每个效果只交**一个**推荐的完整候选（`待验收版`），附参考对照、导出预览、简短说明：解决了什么、还有哪些不影响主要目标的差异、素材在哪。未经 UE 实机验证的部分如实写。
- 做不到时集中报告具体阻碍和已试过的方法，不交低完成度版本。技术结果和小证据可以随时同步，但不算交付。

## 内部迭代闭环（AI 自己跑，不每轮问用户）

参考分析 → 分层与运动关系 → 实现（缺能力先补模拟能力）→ 本机 GPU 计算 → 读结果、视觉自检 → 修正 → 再算 → 导出与回放检查 → 提交完整候选。
- 结构先对：同一批星的连续阶段必须保持轨迹关系，不能用几个互不相关的球形层拼近似画面；模板表达不了就先补能力。
- **不许用降低误差的捷径**：调暗某层、隐藏关键特征、模糊画面、改变取景都不行。拟合分数只作辅助，按视觉差异决定下一轮改什么；连续几轮没改善就重新诊断模型或目标，不盲目加算力。
- 做法参照金芒菊（`协作/金芒菊复盘.md`），不照搬参数和分数。
- **自检按「开花后同一秒」对照实拍**（2026-09-30 晚教训）：拟合对照图按燃烧百分比排，会掩盖时间线错误（外层点亮早晚、变色时刻、熄灭节奏）。开花时刻自动找不准时在条目里填 `burst_t`。
  - 快速（云端 20 秒一张）：`analysis/scripts/时刻对照.py <条目> <图>`，看造型、时间线、颜色；**层间亮度平衡不准**（它每层按探针定曝光，不是烘焙的曝光）。
  - 准的（= 用户在烘焙器里看到的 = 导出贴图）：导出任务自动出的 `烘焙回放.jpg`（实拍 / 实时模拟 / 导出效果，另有 `_原尺寸`）+ `回放检查.jpg / .json`（按 cascade.json 播贴图，查裁切 / 空帧 / 跳变）。进「待我验收」前必须看这张。云端也能出：`window.FW_LIB_TEX = 512` 后调 `export_job.baker_strip`（4 分钟左右）。
- **合并输出（灰度查 Ramp）的暗部会被压得很暗**：一层里亮度随时间变化大（开花一下很亮、后面是点）时，整张一起定曝光会让中后段看不见。这类层用「按帧定曝光」（`expoMode: 'frames'`）。组合页的迭代 / 正式库层现在按条目自己的输出方式烘（和导出一致），以前按「分开输出」叠，看起来比导出亮——不要再拿旧组合页截图当证据。
- 颜色段最多 5 段（第 6 段起会被丢掉）。延时出现的层用 `trimLead`（默认开）不把开头空白烘进贴图。
- 派生新版本：`手调组合.py`（来源是拟合任务或手调组合）/ `派生组合.py`（任何条目，可 `--dup` 复制层做「尾巴层 + 星头层」）。重的效果（大组合）用 GPU：写不拟合、带 `variants` 的任务（多层键 `0.x` / `0+1.x` / `*.x`）或导出任务，几秒一组。

## 条目的形式（用户 2026-09-29 晚明确要求，必须遵守）

- **每条迭代条目都要和正式库条目一样可用**：点开就是一个花型 / 配方，右栏参数齐全可调，中间「实时模拟 / 导出效果 / 贴图」三页都有内容，能按正式流程导出（贴图、Ramp、Cutout、参数表、`cascade.json`）。实拍并排只是辅助对照，可以关，**不能只有视频对比**。
- **按花型库和正式库的形式迭代，不是按参考镜头复刻**：
  - 从花型库模板（菊、牡丹、芯入、变色、锦冠、尾缀 V5……）出发配参数，输出的是游戏素材的镜头和形式（例：尾缀用 V5 的弹体坐标、16×1 循环 + 消散；大面片用固定 / Zoom 取景），不是把实拍视频的机位、构图原样搬过来。
  - 参考视频用来定原理、颜色、时间、比例，不决定输出形式。
- 反例（被否过的）：物理尾缀 TP1 / TPS–TPL 用实拍的跟拍镜头、导出效果和贴图页为空；JM2E、PW3 是 asset 条目，右栏没有参数。

## 还原的做法（用户 2026-09-29 要求：高质量、高效率，分析要对）

- **第一步：效果原理解析（AI 自己完成并据此实现）**：
  对照花型库模板，写清对应模板、分几层、每层轨迹关系 / 颜色时间线 / 有尾无尾 / 熄灭方式、烘焙器缺什么结构，配关键帧截图，写进 `analysis/原理/<效果>.md`。**不再等用户逐项核对**（2026-09-30 14:46 起）；只有参考无法判断、选择会改变目标时集中问，并给推荐。
- **然后做配方分析，再拟合**：`star_analysis.py`（星数、半径、外圈占比、火花尾、颜色、熄灭分布、下坠）+ `star_colors.py`（线性光颜色）+ 看逐帧原图，
  把实拍翻译成化学结构（分层星、木炭尾、变色时刻、集中 / 陆续熄灭），写进 `analysis/花型配方分析.md`。结构和能量出来的量在起点里定死，拟合只调亮度、大小、星数（带上下限）、相机曝光。烘焙器缺的结构先补。
- 下发前在云端用 compare.py 跑一次起点，确认 10% / 50% / 90% 的结构对了再发。
- **结果回来后自己判断**：不够还原就直接分析原因、改、继续下发下一轮，不用等用户；达到「进入待我验收的条件」才交。每轮都写 `看法.md`。
- **拟合分数低不等于通过**：只有用户在「待我验收」里点「通过」才算，才能进正式库。

## 贴图命名与素材包（用户 2026-09-29 晚改：按 spec 示例）

- **导出的素材包按 `spec/` 的写法**：一个效果一个目录 `<效果名>/`，里面是 `cascade.json`（`fwl.cascade/1`）和它引用的贴图，文件名固定、不带日期 / 版本 / 格子：
  `T_<效果名>.png`（序列）、`T_<效果名>_Ramp.png`、`T_<效果名>_Cutout.png`（例：`T_JinMangJu_Zoom.png`）。格子数、帧数写在 `cascade.json` 里。
- 引擎里的正式名字（`T_EFX_FireWorks_…`、两位序号）由本机导入工具在导入时指定，不由烘焙器决定。
- 平台：**PC 和手机两套都要**。纯粒子发射器 PC 写 `"gpu": true`、手机写 `false`；大面片母版一律 CPU。
- 大面片取景只用固定 / Zoom（紧凑禁用）。
- 旧命名 `T_EFX_FireWorks_<名字>[_<部件>]_<列>x<行>_<序号>`（2026-09-28 定，60_export.js 的 `TN()`）是过渡期写法，改完导出（`交接.md` T3）后作废。
- 导出任务自动生成 `preview.js`（`export_preview.py`），可作 asset 补充预览，但迭代区主条目要是正式库形式（见上）。

## 每次收尾必须做

1. 更新 `协作/状态清单.json`（阶段、版本、进度、缺什么），跑 `review_to_baker.py`；`更新记录.md` 最上面加一条：做了什么，**只有进了「待我验收」的才写「要你看」**。烘焙器顶栏「更新记录」显示它，有新条目时按钮上亮一个点（不自动弹出，不挡画布）。

3. 更新 `PROGRESS.md` 的复刻进度表。
4. build、commit、push（提交说明写清楚改了什么），push 成功后再告诉用户。
