# 三套工作流的统一设计语言

本轮比较的是同一主题下三种调参顺序。蓝灰/青绿、接近直角的轮廓、细边框和库—画布—检视器的主要布局保持共同基础；A/B/C 使用同一真实配方、参数控件与草稿状态模型。B 是目前的建议起点，仍由实际制作习惯决定最终选择。

这份说明记录设计判断与实现边界，不代表整页、无障碍、生产迁移或用户验收全部通过。实际验证范围以本轮检查报告为准；旧稿与正式配方继续保留。

## 1. 同一主题怎样建立新层级

层级依次是：工具与配方身份 → 当前编辑层 → 当前任务组 → 原参数与实际值 → 必要原因、帮助与来源。身份只在共用外壳常驻；参数面板无需再重复一整套对象名称与路径。

| 层次 | 共同表达 | 本轮适配 |
| --- | --- | --- |
| 工作区 | 蓝灰低表面、面板与高表面 | 靠表面差异、间距与细分隔建立区域关系，控制嵌套容器数量 |
| 当前对象与主要动作 | 青绿选中及主动作、可见焦点 | 当前编辑与当前观察分别命名；保存与交付动作有明确作用范围 |
| 参数 | 中文持久标签、实际值、独立可读单位 | 字段以13px为主要阅读尺度，辅助信息以12px呈现；名称、原因和错误允许换行 |
| 状态 | 文字加语义颜色 | 改动、错误、只读和未接通分别说明；青绿选中不能代替操作成功 |
| 细节 | 就地帮助、原归属与来源 | 次要说明按需展开；当前不能修改或改了无效的原因直接可见 |

颜色来自正式 `tokens.json`；候选 `u-*` 别名消费同一色值。三套草稿的密度与组织方式属于本轮提案，不能据此覆盖已认可的正式组件形状或状态。画布和Ramp继续承担产物判断，不随界面主题改色。

## 2. 当前组件库的成熟度

正式基础库已有版本化 tokens、离线图标、原生控件、状态样板和作用域约束，README 的 v0.2.1 节记录了烘焙器4.9.125起的接入。此前候选v3又建立了组件映射、状态样板与独立业务Demo。这些是可复用基础，能够支撑本轮统一画风和基础交互。

目前仍有三类不足：

- **基础与候选尚需收口。** `fw-*`正式基础和`u-*`候选适配仍并存；文档中早期“尚未接入三个正式工具”的概述与后续烘焙器接入记录也需统一，不能概括成三工具迁移完成。
- **领域组件还依赖业务适配。** 参数条件、树、观察对象、时间轴、烘焙与交付回执具有各自模型。基础表格、按钮或弹窗存在，不等于完整制作流程已经由组件库覆盖。
- **组件状态样板不能证明整页质量。** 中文长名、长数字、窄栏、缩放、焦点接续、失败恢复及实际数据依赖仍须在真实入口核对。当前三稿也只覆盖代表参数，不是生产参数全集。

本轮增加的价值是将参数输入和草稿行为集中到共用层，再让三种面板只负责信息组织。选定方向后，适合复用的行为再登记为正式组件；现阶段不应把三套独立样式同时当作正式标准。

## 3. 共用参数模型与四组投影

`studio.js`中的`renderField(param, options)`为三套方案生成同一套数值、滑杆、枚举和颜色控件，统一单位、校验、只读/锁定/条件原因、标签及错误关联。面板消费同一模型和事件委托，不各自维护另一份值、撤销或保存逻辑。C中同一参数的表格精确输入与展开滑杆也指向同一个字段。

40个代表字段来自GLB-S1「金曜菊-B · 疏点游闪」金锦层原配方、生产SCHEMA和名称表。保留原字段ID、值、单位与含义；完整P/M及另外两层的真实上下文仍在`parameters.json`中。金锦可编辑，橙引线层与点灭星供只读核对。本轮仍编辑单个对象，没有多对象混合值或批量改参。

| 草稿任务组 | 方便回答的问题 | 原归属仍保留 |
| --- | --- | --- |
| 外形 | 数量、排布、颗粒尺度和空间密度如何构成外观 | 星/火花的生成、形状与大小 |
| 运动 | 如何展开、受力、燃烧和消散 | 初速、受力、寿命及原效果规格/环境 |
| 光色 | 亮度、温度、冷却、闪烁与Ramp如何配合 | 原亮度、颜色、闪烁及光点角色 |
| 输出 | 曝光、时段、取景、格子和平台方案如何设置 | 原输出模块与产物设置 |

四组是找参数的任务投影，不是生产模块重命名。原“层 → 发射器 → 模块/节”继续可追溯；一个新组名也不会改变参数控制方向。例如星体终端速度与火花阻力仍是不同物理字段，不能为了分组统一叫作“阻力”。具体条件与字段审查见[workflow-audit.md](workflow-audit.md)。

## 4. 三套方案共用的状态规则

状态有不同判断轴，不能压成一个“正常/异常”标签。一个值可以同时“相对原配方已改、尚未保存、当前条件无效”。

| 状态 | 判断依据 | 用户看到或能做什么 |
| --- | --- | --- |
| 只读 | 当前层是本轮真实参考对象 | 原值仍可阅读；明确说明本轮可编辑金锦层，不把金锦值复制给其他层 |
| 锁定 | 用户主动锁住可编辑层 | 值保留，解锁后继续编辑；不会关闭输出或改变当前观察对象 |
| 条件无效 | 当前值满足原业务的无效条件 | 保留原值并显示原因；例如星头亮度为0且未启用跟星头大小时，星头大小不产生可见变化 |
| 输入错误 | 内容不符合已建立的输入规则 | 就地显示具体错误与修正方向，保留待修正输入；错误值不送入实时预览，有错误时不能保存Demo |
| 未保存 | 当前草稿与本方案最近成功保存快照不同 | 保存成功才更新保存快照；保存失败仍保留内存中的当前编辑 |
| 相对原配方已改 | 当前参数值不同于固定初始配方参考 | “仅改动”、改动数和参数恢复均按这一基线；保存、刷新Demo不会清除这类差异 |
| 已保存Demo | 本方案独立浏览器存储写入成功 | 表示本地Demo草稿已保存；原配方参考仍保持固定 |

API字段仍叫`initialValues`，其含义是**固定的原配方参考值**；`savedValues`是另一条独立保存快照。当前值相对原配方有差异，并不必然意味着尚未保存。

切换组、搜索、英文名、观察方式或窄屏窗格只改变呈现与定位。实际参数修改、撤销/重做、恢复和保存由同一控制器负责；选定方案后仍需将其键盘与焦点行为核对到实际入口。

### 范围、单位与来源

SCHEMA的`min/max/step`在本轮表示常用滑杆区间及调整增量；没有从原业务建立可靠硬边界时，`hard_bounds`为`null`。超出常用区间的有限手输值需要说明，不能静默截断，也不能把滑杆增量新增为全部输入的合法性规则。颜色、枚举和数值各按自己的类型校验；单位保持原字段含义。

每个字段的`source`记录文件、行号与来源角色，`originalGroup`记录原发射器/模块/节。用户可从说明追到原归属，再按需展开精确来源。配方指纹和来源工具版本描述摘录依据，不是给Demo虚构一个生产版本，也不代表效果已验证。

### 观察、编辑与输出

选层名决定编辑对象；观察选择决定画布看什么；眼睛开关决定Demo记录的输出启用配置。三者独立，名称与状态必须分别表达。

本轮真实预览只接选层实时渲染核，按本层秒数运行。原组合中金锦层的速率1.5仍可见，但单层预览不证明整朵同步。整朵静态参考明确标为静态，另两层保留真实只读值。输出选项只记录待烘焙设置；没有据此生成素材包、目录交付或UE回执。

Demo保存使用A/B/C各自的独立状态，不写正式配方或用户个人节目。草稿JSON也只用于界面评审；“形式检查完成”“成功保存Demo”“已烘焙”“已导出”“UE已验证”和“用户认可”是不同事实。

## 5. 官方依据与本项目判断

资料核对日期：2026-10-29。三个来源共同用于三套方案，A/B/C不对应任何品牌外观。

| 官方依据 | 采用的原则 | 本项目的适配判断 |
| --- | --- | --- |
| [Spectrum Slider](https://spectrum.adobe.com/web/rsp/components/slider)、[Number field](https://opensource.adobe.com/spectrum-web-components/components/number-field/) | 快速粗调与精确输入配合；完整标签、键盘操作及可换行帮助/错误 | 原物理单位和输入规则优先，常用滑杆区间与业务硬边界分开；当前模型只处理单对象值 |
| [Fluent Toolbar](https://fluent2.microsoft.design/components/web/react/core/toolbar/usage)、[Accessibility](https://fluent2.microsoft.design/accessibility) | 相关动作归组，清楚的图标标签，顺着信息层级导航与恢复焦点，缩放时保留信息 | 主动作、当前对象与参数过滤各有位置；窄屏切换呈现窗格，不切对象或扩大执行范围 |
| [Carbon Forms](https://www.carbondesignsystem.com/building-blocks/core/patterns/forms)、[Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines) | 持久标签、对齐、就地必要帮助、清楚列头与按需展开 | 中文长名和错误可以增高行，C用连续表格承载差异；必要原因不因追求固定密度而隐藏 |

以上是选用行为原则后的项目判断，不是照搬组件包。官方体系自身的无障碍声明，也不能转移成FireWorksLab当前整页已达标的声明。

## 6. 用户只需选择的取舍

| 默认工作方式 | 更容易完成的事 | 需要接受的代价 |
| --- | --- | --- |
| A · 连续检视 | 跨组连续阅读，同时对照和联调多个参数 | 纵向内容更长，需靠锚点、折叠和滚动维持位置 |
| B · 分组聚焦 | 一次集中处理外形、运动或光色，减少同屏干扰 | 跨组联调需要切换，需依赖当前值与状态接续 |
| C · 参数对照 | 先核对相对原配方的差异，再对选中项精调 | 详细说明与滑杆按行展开，连续调很多项要反复定位 |

目前建议先以B作为日常制作起点，因为它更容易把当前任务和可读密度维持在一处。这只是建议：经常跨组连调时A更顺，主要先核对差异时C更直接。用户只需决定更符合习惯的默认信息组织；共用主题、真实字段含义和状态边界无需重新选择。
